# Бекенд

- FastAPI для обробки запитів, там має бути два маршрути:
  - /chat — обробка повідомлень (WebSocket).
  - /health — формат відповіді, наприклад, { "status": "ok", "uptime": "..." }.
- Інтеграція з OpenAI GPT-5.
- Логування діалогу й іншої інформації в PostgreSQL, там потрібні таблички:
  - Історія чатів
  - Замовлення (зробити під капотом максимально схожу по можливості до Odoo sale.order)
  - Клієнти
  - Повідомлення
  - Налаштування чат-боту
  - Користувачі
  - Таблиця для збереження налаштувань параметрів системи.

За потреби можна доповнювати полями.

# Ролі та права доступу

Системний адміністратор:

- Має повний CRUD доступ до ключів (Налаштування параметрів системи)
- Має права Адміністратора

Адміністратор:

- Заводить користувачів і встановлює права доступу (Користувачі)
- Налаштовує промпт й бізнес-контекст бота (Налаштування чат-бота)
- Має права Менеджера

Менеджер:

- Має доступ до тестування бота
- Бачить історії спілкування з клієнтами (ніяких змін з ними не робить)
- Бачить замовлення клієнтів (може максимум позначити як опрацьоване)

# Основні сторінки

- Сторінка логіну
- Сторінка для тестування чат-бота
- Сторінка для налаштування чат-бота
- Сторінка з історією замовлень (табличка)
- Сторінка з історією чатів клієнтів (табличка)
- Сторінка з можливістю внесення нових користувачів та налаштування їм прав доступу (просто табличка)
- Сторінка з налаштуваннями, де можна налаштувати Telegram ключ і OpenAI ключ.

## Логіка роботи чат-бота

Приходять вхідні дані на Websocket (за необхідності розробники можуть їх доповнювати):

```json
{
  "session_id": "487438957jfhewjrhew",
  "sender": "user",
  "message": "Які є знижки на цей бокс?",
  "timestamp": "2025-08-15T11:27:00Z"
}
```

Потім ми з ними працюємо:

- За `id` розуміємо чи це продовження переписки чи нова
- Передаємо це запитом в GPT, від якої очікуємо:

  - Відповідь на питання клієнту (response)
  - Чи потрібно перевести комунікацію на менеджера,це потрібно у деяких випадках:

    - Бот не впевнений у відповіді (низька впевненість від AI-моделі).
    - Запит поза сценарієм (бот не має інформації, наприклад, нестандартна проблема клієнта).
    - Емоційно важливі кейси (скарги, конфлікти, VIP-клієнти).
    - Технічні або фінансові обмеження (наприклад, зміна умов замовлення, повернення коштів).
    - Прямий запит користувача ("Хочу говорити з менеджером").

  - Для реалізації цього отримуємо від GPT поля:

    - handover_to_manager (boolean), якщо true - надсилаємо повідомлення в телеграм.
    - handover_reason - вибір з класифікації причин:

      ```json
      {
        "LOW_CONFIDENCE": "Бот не впевнений у відповіді",
        "OUT_OF_SCOPE": "Запит поза сценарієм / бот не має інформації",
        "SENSITIVE_CASE": "Емоційно важливий кейс (скарги, конфлікти, VIP)",
        "TECH_OR_FINANCIAL_LIMITATION": "Технічні або фінансові обмеження",
        "USER_REQUEST_MANAGER": "Прямий запит користувача на менеджера"
      }
      ```

    - handover_reason_description (короткий текстовий опис причини передачі).Наприклад:

      ```json
      {
        "response": "Ми пропонуємо знижку 10% на цей бокс при замовленні від 3 штук.",
        "handover_to_manager": true,
        "handover_reason": "LOW_CONFIDENCE",
        "handover_reason_description": "Клієнт продовжує вимагати знижку, якої немає в системі"
      }
      ```

- Відповідь ми повертаємо клієнту, всю іншу інформацію якщо handover - менеджеру плюс інформацію про чат з клієнтом.
- Далі, коли менеджер отримав цю інформацію він може зайти у нашу програму бачити чати переведені на менеджера та позначати їх як “в роботі менеджера” та “вирішені”. Нехай на сторінці чатів їх можна буде відфільтрувати за Inbox (ті, які потребують втручання людини):
  - список чатів у статусі HANDOVER_PENDING/ HANDOVER_IN_PROGRESS
  - панель повідомлень ( історія, поле вводу)
  - кнопки дій: "Позначити як вирішений".

Все повинно логуватися у тій самій сесії. У таблиці messages, з полями, наприклад, за потреби можуть доповнюватися:

- chat_id
- sender - це {user, bot}
- channel - це {web, telegram, …} (поки що web)
- text (відповідь, тощо)
- timestamp

Пропонована модель станів (для conversations.handover_state):

- NONE — звичайний діалог з ботом.
- HANDOVER_PENDING — GPT сигналізував про передачу, нотифікація в Telegram/Inbox відправлена, менеджер ще не взяв.
- HANDOVER_IN_PROGRESS — менеджер “взяв у роботу” (assigned_to = user_id).
- RESOLVED_BY_MANAGER — менеджер закрив кейс (за потреби — з підсумком).
